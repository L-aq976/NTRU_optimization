## 2. 改动与原因（按重要性）

### 2.1 噪声模型：把"跳"化简成"和"

h 跳链解密端的噪声核（已在代码与文档中推导并核实）：

```
T_h = g·s + F_A·M + Σ_{i=1..h} e_i·f_Bi
f_Bh·C_Bh = p·T_h + M
```

关键结构：`Σ(g)=Σ(F_A)=Σ(e)=0` 且 `Σ(f_B)=1` ⇒ **Σ(T_h) 是常数** ⇒ 系数零均值、方差随 h 线性增长。
这正是大偏差/鞍点分析的标准结构，也是尾部模型能成立的前提。

**为什么重要**：`T_h = C0 + Σ W_i`（C0 与 W 独立），于是

```
K_{T_h}(t) = K_C0(t) + h·K_W(t)
```

鞍点可以对 h **解析放大**，不需要为每个 h 重新做一遍经验估计。这是尾模能便宜地覆盖几十个 h 的原因。

### 2.2 C1（门限）耦合：一个极简的改写

门限组合是把全部 `m = C(N,t−1)` 份 partial 直接相加，每份各带一个 `p·e_S` 且**共用同一个** `f_B`：

```
Σ_S (C_A·share_S + p·e_S) = C_A·rk + p·Σ_{k=1..m} e_k
```

⇒ **门限版完全等价于基线把 `e_i` 换成 `Σ_{k=1..m} e_k`**。

**为什么重要**：由此每跳仍只做**一次**卷积，代价只是 O(m) 次采样。否则 m=56 的配置要付 56 倍卷积开销，门限联合表根本跑不动。代码里就是 `sample_sum_fixed_weight(..., m)`。

### 2.3 修掉的四个真 bug（都是靠硬断言抓出来的）

#### (a) `1 + p*F` 在 numpy 里给每个系数都加 1

环里的 "1" **只是常数项**。原来写 `1 + P.p * F_B` 会让整个 `f_B` 错掉（应该是 `f[:,0] += 1`）。
→ 新增 `sample_fB()` / `const_one()`，并加断言：`f_B` 常数项 ∈ {−2,1,4}、其余 ∈ {−3,0,3}、`Σ(f_B)=1`。

#### (b) `np.argpartition` 的输出槽位排列与输入下标相关 ★ 最隐蔽

固定重量三元的采样要"随机选 2d 个位置，前 d 个记 +1、后 d 个记 −1"。我原来直接按 argpartition 输出的槽位分符号。实测：

```
给定下标 0 被选中，它落在前 `plus` 个槽位的概率是 0.70 —— 不是 0.50
```

于是 **+1 系统性偏向低下标**，把 `Var(g·s 系数)` 从理论值 **154** 抬到 **737**（4.8 倍）。

**修法**：另取一组**独立的**随机数再做一次排名来分配符号，切断与选择步骤的关联。
**防复发**：新增断言 `Var(g·s 系数) == 4·dg·dr/n`（相对误差 15% 内）。这条断言以后能防住同类问题。

> 这个 bug 值得单独说：它不会让程序崩、不会让量级明显异常，只会让分布悄悄偏掉 —— 而 C2 的全部结论都建立在分布上。

#### (c) 素数长度 FFT 退化成 Bluestein

`n ∈ {439, 1087, 1171, 1499}` **全是素数**，直接怼循环 FFT 会让 numpy pocketfft 走 Bluestein。改成**补零到 2 的幂做线性卷积再折回**，实测快 **1.4–1.9×**，且仍然逐位精确。

#### (d) 明文必须用 mod p 表示，不能用中心表示 ★ 影响最大的一条

我原本把明文采样成中心形式 `{−1,0,1}`。但 C++ 的 `sample_message` 是
`mod_q(t[i], p)`，即 **−1 变成 p−1 = 2**（这一点在导出的 vectors 里也看得到：`M ∈ {0,1,2}`）。

**两者在环里等价**（差 3·k，k 是"−1 处"的指示），但**在 Z 上不等价** —— 噪声核里 `F_A·M` 那一项会差 `3·F_A·k`。

拿真实的 `T_1` 直接量（`bin/vectors_EES439_7.txt`）：

| 明文表示 | `T_1` 的 std | 与真实 `T_1` 逐位相等 |
|---|---|---|
| **mod p**（C++ 实际用法） | **42.6** | ✅ |
| 中心（我原来的写法） | 40.0 | ❌ |

差别只有 ~6% —— 因为 `M_cent` 与 `k` 是互补的，两者强反相关，把 `3·F_A·k` 的效果大部分抵消掉了。
（我一开始按独立随机估 `Var(3·F_A·k) ≈ 1533`，完全错了；实测量到的总方差差只有 215。）

**但 6% 的噪声尺度差，在指数敏感的尾部就是约 60 倍的 δ 差**，而且它**主要影响小 h**：

| | σ_T(h=1) | σ_T(h=5) |
|---|---|---|
| 中心表示 | 42.7 | 88.6 |
| mod p 表示 | 45.2 | 89.8 |
| 差 | **+5.9%** | +1.4% |

所以 δ(5) 那类"悬崖附近"的数字几乎不动（论文锚点对拍仍然有效），但 `δ(1)`、`h_max(2^-40)` 这类深尾数字必须重算。

**修法**：明文改按 mod p 采样，判据改为与明文的中心表示比（对应 C++ 的 `message_equal`）。
**防复发**：新增断言"明文系数 ∈ [0,p)，且有 dm0 个 1、dm1 个 p−1"，并保留那条与 vectors 逐位对拍的断言
—— 后者正是发现这个问题的工具（它用 vectors 的**原始** M 才比对得上，逼我去查表示差异）。

### 2.4 采样器 / 后端 / 性能

- 采样复现 `src/core/sampler.cpp` 的固定重量语义（无放回均匀子集）。
- 三个后端：`exact`（int64 参照）、`fft`（CPU 默认）、`cupy`（WSL/GPU，复用 `gpu_kernel.py` 的 `HAS_CUPY` 分派写法）。
- 浮点 FFT 的无损性有明确误差界：操作数 ≤ `dr·4 = 504`、补零后长度 ≤ 4096，舍入误差 ≲ 1e-7 ≪ 0.5，约 6 个数量级余量。仍以 `fft == exact` 逐位硬测兜底。

### 2.5 标定：按事件数加权

`δ̂` 在 log 空间的方差约 `(1−δ)/(N·δ)`，所以权重取 `failures/(1−δ)`，并丢掉事件数 < 30 的点。
**原因**：EES1087 的标定残差原来被几个只有 5~13 个失败事件、δ 本身有 ~45% 相对误差的点主导，报出 0.25 decade；加权后降到 0.16 decade，剩下的主要是真实的系统性漂移而不是噪声。

### 2.6 新增"漂移"指标（不是噪声，是信号）

标定区内 `log10(δ_MC/δ_模型)` 的**极差**单独作为一列输出。它才是**外推不确定度的主项**：残差小只说明模型形状在可测区内对得上；比值随 h 单调漂移说明并集界 `δ≈n·p₁` 的紧度在变（h 大时系数趋于独立、界收紧），外推到更小的 h 时这个偏差会继续走。代码里超过 0.05 decade 就打印警告，**不靠拟合抹平**。

### 2.7 顺带修掉一个 Windows 构建坑（不是源码 bug）

跑回归（`python pyref/cross_check.py EES439 7`）时发现 `ntru_cli vectors` **必段错误**，而 `selftest` / `smoke` / `bench` 全都正常。

排查过程：`-O0` 编译正常、`-O2` 崩溃 → 典型的 UB 症状；用 `g++ -g -O2` + `gdb -batch -ex run -ex bt` 拿到栈：

```
#3  std::basic_ofstream 构造函数   at D:/mingw64/include/c++/16.2.0/bits/ostream.h
#0  libstdc++-6.dll  from  D:/yanwenji/Git/mingw64/bin/
```

**根因不是源码**：编译用的是 `/d/mingw64`（g++ 16.2.0），但运行时 PATH 上排在前面的
**Git for Windows 自带的旧 `libstdc++-6.dll`** 被加载了 —— 两套 MinGW 运行库 ABI 不一致。
`selftest` 等命令从不创建 `ofstream`，所以躲过了；**`vectors` 是唯一写文件的子命令**，崩点正好在 `basic_ofstream` 构造里。

**修法**：`build.ps1` 加 `-static-libstdc++ -static-libgcc`（已加，并写了注释说明为什么不能省）。
重建后 `cross_check.py` **9 项全过**，且 C++ 算出的 `‖center(f_B·c_B)‖∞ = 361` 与本项目 Python 侧独立算出的 361 完全一致。

> 这条也写进了 `README.md` §6 环境坑。它不改变任何算法，但**解开了被卡住的 `cross_check.py` 工作流**（README §3 一直在推荐它）。

### 2.8 跑批太慢 —— 原因与修法

**症状**：门限联合表（20 个配置）起了之后，25 分钟只跑完 4 个（还都是最小的 EES439），照这个速度要 45–60 分钟。

**实测分解**（EES439 + m=1，最便宜的一个配置，此时还有别的任务在抢 CPU）：

| 阶段 | 耗时 | 是否必要 |
|---|---|---|
| `choose_max_hops`（pilot MC） | 16.8 s | 可大幅削减 |
| `simulate_curve`（14 跳 × 3 万样本） | 32.6 s | **必要**（数据本身） |
| `sample_common_part`（20 万样本的 C0） | 20.9 s | **只需一次，却每个 m 重算** |
| `sample_increment`（20 万样本的 W） | 10.6 s | 必要（且**随 m 线性增长**） |
| `TailModel` 构造（192 网格点） | 1.2 s | 必要 |
| **合计** | **≈ 82 s / 配置** | |

**三个原因，前两个是我的设计失误**：

1. **32 核的机器，我串行跑**（最大的一条）。20 个配置一个接一个，每个都是纯单线程 NumPy —— 机器 31 个核在闲着。
2. **C0 白算了 16 次**。`sample_common_part` 的调用签名里**根本没有 `m`** —— C0 只依赖参数集，我却对每个 m 重算一遍。4 个参数集 × 5 个 m 里，有 16 次是纯重复。
3. **`--cgf-samples` 从 6 万提到 20 万（3.3×）**。这是为了修深尾收敛性（见 §5），**本身是对的、必要的**，但代价是**每个配置各付一次**，20 个配置就是 20 次。

> 真正的教训不是"哪一步慢"，而是**我没先量一个配置的成本就直接起了 20 个**。跑之前花 80 秒量一次，就能避免这半小时。

**修法（已实现）**：

| 改动 | 效果 |
|---|---|
| `ProcessPoolExecutor` 并行，新增 `--jobs`（默认 8） | 20 个配置分摊到多核；配置之间彼此独立，天然可并行 |
| C0 移出 `analyze`，改为**每个参数集只算一次**再传给各 m | 省掉 16 次重复的 20 万样本估计 |
| pilot 样本 4000 → 2000、cap 60 → 40、`stop_delta` 0.995 → 0.99 | 探针只用来找饱和点，不需要精确 δ |
| `auto_chunk()`：按 n 反推 CGF 采样的批大小 | 进程池下内存峰值可控（n=1499 时 8192 → 1334） |

**踩过的坑**：一开始用 `ps -W \| grep python` 看不到子进程，以为并行没生效；实际上 Windows 的 spawn 方式起的 worker 匹配不上那个正则 —— 要用 `tasklist` 看（17 个进程 = 1 父 + 16 子，各 100~400 MB）。

### 断言 2 是这次最有价值的一条

它拿 C++ 引擎**真实算出来的密文**（`f_B`、`C_B`、`M`、`g`、`s`、`e`、`F_A`）反推出噪声核，与我们的模型公式逐位比对 —— 模型公式不是我推完就算数，是被实数验过的。

过程中还澄清了 vectors 导出的两个表示问题（写进注释，避免后踩）：
- 导出的 `FA` 其实是 **`f_A`**，要 `F_A = (f_A − 1)/p` 才能还原（`1` 只在常数项）；
- 导出的 `M ∈ {0,1,2}` 是 **mod p 原样表示**，不是中心形式 `{−1,0,1}`；
- `f_B·C_B` 必须**先归约 mod q 再取中心代表**，才是环里真正的"小多项式"。

### 4.1 论文 Table 4 锚点对拍 ★

设计文档的说法是"论文 Table 4 的经验跳数对应**约 10% 的解密失败率**"。

| 参数集 | 论文经验跳数 | 我们算出的 δ(MC) | 95% CI | δ(模型) | 结论 |
|---|---|---|---|---|---|
| EES439 | 5 | **5.15%** | [4.90%, 5.40%] | 4.98% | ✅ 与 ~10% 同量级 |
| EES1171 | 21 | **8.82%** | [8.50%, 9.14%] | 8.50% | ✅ 对上 |
| EES1499 | 50 | **12.65%** | [12.28%, 13.03%] | 12.83% | ✅ 对上 |
| EES1087 | 21 | **56.73%** | [56.16%, 57.28%] | 55.38% | ❌ **对不上** |

（参考：各参数集 δ 最接近 10% 的跳数分别是 EES439 = **5**、EES1087 = **15**、EES1171 = **21**、EES1499 = **48**。）

### 4.2 跳数预算表

| 参数集 | 论文跳数 | h_max(δ=1e-3) | h_max(δ=1e-6) | h_max(δ=2^-40) |
|---|---|---|---|---|
| EES439 | 5 | 3 | 2 | 1 |
| EES1087 | 21 | 9 | 5 | 3 |
| EES1171 | 21 | 13 | 8 | 4 |
| EES1499 | 50 | 30 | 19 | 10 |

**读法**：论文的经验跳数大致落在 δ≈10% 那一档；要压到 `2^-40`，可用跳数大约要**砍掉一半到三分之二**。这就是"把经验跳数升级成预算"要给的数字。

### 4.3 门限（C1）的代价曲线 ★

`m = C(N,t−1)` 是门限化后每跳多出的噪声份数（见 §2.2）。**目标 δ = 1e-3** 时：

| 参数集 | m=1（基线） | m=3 | m=5 | m=10 | m=15 |
|---|---|---|---|---|---|
| EES439 | 3 | 1 (−2) | 0 (−3) | 0 (−3) | 0 (−3) |
| EES1087 | 9 | 3 (−6) | 1 (−8) | 0 (−9) | 0 (−9) |
| EES1171 | 13 | 4 (−9) | 2 (−11) | 1 (−12) | 0 (−13) |
| EES1499 | 30 | 10 (−20) | 6 (−24) | 2 (−28) | 2 (−28) |

括号内是相对基线的**跳数损失**。这就是 C1 + C2 的结合点：
**把腐化阈值从 1 个代理提到 t 个代理，代价是可支持跳数大幅下降**
（最极端的 EES1499 在 m=15 时从 30 跳掉到 2 跳）。

> 完整数据（4 个目标 δ × 4 参数集 × 5 个 m）见 `bench/results/c2_threshold.csv`。

### 4.4 ⚠️ EES1087 的不一致 —— 需要你和论文核对

我们的模拟对 EES1087 给出 δ(21) = 56.7%，而设计文档认为论文 Table 4 的"21 跳"对应约 10%。

**这不是模拟出错，是参数本身的差异**：噪声的每跳增量标准差

```
σ_W ≈ 3·sqrt(4·dr·df/n)
EES1087: 3·sqrt(4·120·120/1087) = 21.8
EES1171: 3·sqrt(4·106·106/1171) = 18.6     ← 只差 17%
```

**17% 的噪声尺度差，在指数敏感的尾部就放大成 8.8% vs 56.7%**。也就是说两条曲线本身是自洽的，问题在于：论文 Table 4 的 EES1087 那一行到底是用什么判据测的？

**三个可能**，需要查原文确认：
1. 论文 Table 4 各行对应的失败判据不完全相同；
2. `mc_failprob.py` 里 `Config` 的 `paper_hops` 对 EES1087 是猜的/抄错的（原始来源 `A1-4_选题方案/multihop_output.txt` 不在本机，无法核对）；
3. EES1087 的参数组装（`df/dg/dr`）与论文原本的 EES1087 不同。

**在查清之前，报告里不能写"四个参数集全部复现了论文 Table 4"**，只能写"4 个里有 3 个对上，EES1087 存在待查的不一致"。

## 5. 已知限制与不确定度（必须写进报告）

1. **深尾外推的绝对数值只有量级意义。** `δ(1)` 从 `4.7e-15`（EES439）到 `1e-81`（EES1499），这些数字**完全依赖经验 CGF 的二次延拓**，而延拓的锚点 t_max 受样本量限制。
   **已做敏感性实测**（EES439，MC 曲线固定，只变 CGF 样本数）。
   这条结论可复现，就是一条命令：

   ```bash
   python pyref/mc_failprob.py --params EES439 --cgf-sweep 50000,200000,800000
   ```

   实测值（40000 样本的 MC）：

   | CGF 样本数 | t_max | δ(1) | δ(2) | δ(3) | h_max(2^-40) | h_max(1e-6) |
   |---|---|---|---|---|---|---|
   | 5 万 | 0.0554 | 7.4e-13 | 1.7e-06 | 4.5e-4 | 1 | 1 |
   | **20 万**（默认） | 0.0726 | 1.9e-14 | 6.4e-07 | 3.6e-4 | 1 | 2 |
   | 80 万 | 0.0830 | 1.3e-14 | 6.5e-07 | 3.6e-4 | 1 | 2 |

   **结论：20 万以上已经收敛** —— 20 万 → 80 万，`δ(1)` 只差 1.5 倍，`δ(2)`/`δ(3)` 基本不动，`h_max` 稳定。5 万不够（`δ(1)` 偏 40 倍、`h_max(1e-6)` 差 1）。
   所以默认的 `--cgf-samples 200000` 是实测选出来的，不是拍脑袋；正式跑批不要往下调。
   - **实用结论稳**：EES1087/1171/1499 的 `δ(1)` 分别约 `1.4e-32` / `5.2e-51` / `1e-81`，都远低于 `2^-40`。
   - 报告里仍应把这些值写成"低于 X 量级"，因为模型还有 §2.6 那个漂移不确定度（实测 0.068~0.124 decade）。
2. **并集界 `δ ≈ n·p₁` 在 h 小时高估。** 这就是 §2.6 那个漂移的来源，已在输出里量化，不能当作已解决。
3. **MC 可测下限**：CPU/fft 在 40000 样本下约 `δ ~ 1e-4`。要测到 `1e-6` 需要 `~1e7` 样本（`--backend cupy`，WSL）。
4. **两个 TINY 参数集（n=7 / n=61）噪声远小于 q/2，永不失败**，只能用于算术精确性验证，不能用于失败概率统计。
5. **两端口径**：C++ 引擎默认用 `mt19937_64`（`sampler.h` 有 CSPRNG 的 TODO）。C2 的模拟器同样用确定性 RNG，**只用于概率建模，不用于生成真实密钥**。
6. **`h_max` 的含义**：它是"δ ≤ 目标"的最大跳数。EES439 在 `2^-40` 下给出 1，是因为该方案**自身 1 跳的算术噪声底**就已经接近这个量级 —— 这是方案的固有属性，不是缺陷。

## 7. 怎么用

```bash
python pyref/hop_sim.py --selftest                    # 全部硬断言（约 40s）
python pyref/mc_failprob.py                           # 4 个 EES 参数集，出曲线+预算表+CSV
python pyref/mc_failprob.py --params EES1171 --samples 200000

# 门限（C1）联合表：m = C(N,t−1)
python pyref/mc_failprob.py --proxy 5:3               # 只跑一个代理配置（N=5,t=3 → m=10）
python pyref/mc_failprob.py --m-list 1,3,5,10,15      # 一组 m 值（常用）
python pyref/mc_failprob.py --joint                   # 等价于 --m-list 1,3,5,10,15
python pyref/mc_failprob.py --m-list 1,5,15 --jobs 16 # 并行度（默认 8；内存紧就调小）

python pyref/mc_failprob.py --input <外部表>           # 老路径，向后兼容
python pyref/cross_check.py EES439 7                  # 回归：既有跨语言校验
```

**调参提示**：`--cgf-samples` **不要往下调**（实测 5 万不够、20 万以上才收敛，见 §5）；
`--samples` 决定 MC 能测到的 δ 下限（4 万样本约到 `1e-4`）；`--jobs` 只在配置之间并行，
单个配置内部仍是单线程。
