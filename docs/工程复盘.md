### 1.1 一句话

C2 从"骨架"变成了**可跑、自包含、且已用 C++ 引擎实数对拍过**的失败概率预算工具：能自己生成 δ(h) 曲线、

## 2. 修掉的四个真 bug（都是靠硬断言抓出来的）

### (a) `1 + p*F` 在 numpy 里给每个系数都加 1

环里的 "1" **只是常数项**。原来写 `1 + P.p * F_B` 会让整个 `f_B` 错掉（应该是 `f[:,0] += 1`）。
→ 新增 `sample_fB()` / `const_one()`，并加断言：`f_B` 常数项 ∈ {−2,1,4}、其余 ∈ {−3,0,3}、`Σ(f_B)=1`。

### (b) `np.argpartition` 的输出槽位排列与输入下标相关 ★ 最隐蔽

固定重量三元的采样要"随机选 2d 个位置，前 d 个记 +1、后 d 个记 −1"。我原来直接按 argpartition 输出的槽位分符号。实测：

```
给定下标 0 被选中，它落在前 `plus` 个槽位的概率是 0.70 —— 不是 0.50
```

于是 **+1 系统性偏向低下标**，把 `Var(g·s 系数)` 从理论值 **154** 抬到 **737**（4.8 倍）。

**修法**：另取一组**独立的**随机数再做一次排名来分配符号，切断与选择步骤的关联。
**防复发**：新增断言 `Var(g·s 系数) == 4·dg·dr/n`（相对误差 15% 内）。这条断言以后能防住同类问题。

> 这个 bug 值得单独说：它不会让程序崩、不会让量级明显异常，只会让分布悄悄偏掉 —— 而 C2 的全部结论都建立在分布上。

### (c) 素数长度 FFT 退化成 Bluestein

`n ∈ {439, 1087, 1171, 1499}` **全是素数**，直接怼循环 FFT 会让 numpy pocketfft 走 Bluestein。改成**补零到 2 的幂做线性卷积再折回**，实测快 **1.4–1.9×**，且仍然逐位精确。

### (d) 明文必须用 mod p 表示，不能用中心表示 ★ 影响最大的一条

我原本把明文采样成中心形式 `{−1,0,1}`。但 C++ 的 `sample_message` 是
`mod_q(t[i], p)`，即 **−1 变成 p−1 = 2**（这一点在导出的 vectors 里也看得到：`M ∈ {0,1,2}`）。

**两者在环里等价**（差 3·k，k 是"−1 处"的指示），但**在 Z 上不等价** —— 噪声核里 `F_A·M` 那一项会差 `3·F_A·k`。

拿真实的 `T_1` 直接量（`bin/vectors_EES439_7.txt`）：

| 明文表示 | `T_1` 的 std | 与真实 `T_1` 逐位相等 |
|---|---|---|
| **mod p**（C++ 实际用法） | **42.6** | ✅ |
| 中心（我原来的写法） | 40.0 | ❌ |

差别只有 ~6% —— 因为 `M_cent` 与 `k` 是互补的，两者强反相关，把 `3·F_A·k` 的效果大部分抵消掉了。
（我一开始按独立随机估 `Var(3·F_A·k) ≈ 1533`，完全错了；实测量到的总方差差只有 215。）

**但 6% 的噪声尺度差，在指数敏感的尾部就是约 60 倍的 δ 差**，而且它**主要影响小 h**：

| | σ_T(h=1) | σ_T(h=5) |
|---|---|---|
| 中心表示 | 42.7 | 88.6 |
| mod p 表示 | 45.2 | 89.8 |
| 差 | **+5.9%** | +1.4% |

所以 δ(5) 那类"悬崖附近"的数字几乎不动（论文锚点对拍仍然有效），但 `δ(1)`、`h_max(2^-40)` 这类深尾数字必须重算。

**修法**：明文改按 mod p 采样，判据改为与明文的中心表示比（对应 C++ 的 `message_equal`）。
**防复发**：新增断言"明文系数 ∈ [0,p)，且有 dm0 个 1、dm1 个 p−1"，并保留那条与 vectors 逐位对拍的断言
—— 后者正是发现这个问题的工具（它用 vectors 的**原始** M 才比对得上，逼我去查表示差异）。

## 3. 另外两个工程坑

### 3.1 Windows 构建坑（不是源码 bug）

跑回归（`python pyref/cross_check.py EES439 7`）时发现 `ntru_cli vectors` **必段错误**，而 `selftest` / `smoke` / `bench` 全都正常。

排查过程：`-O0` 编译正常、`-O2` 崩溃 → 典型的 UB 症状；用 `g++ -g -O2` + `gdb -batch -ex run -ex bt` 拿到栈：

```
#3  std::basic_ofstream 构造函数   at <MinGW-w64>/include/c++/16.2.0/bits/ostream.h
#0  libstdc++-6.dll  from  <Git-for-Windows>/mingw64/bin/
```

**根因不是源码**：编译用的是独立安装的 MinGW-w64（g++ 16.2.0），但运行时 PATH 上排在前面的
**Git for Windows 自带的旧 `libstdc++-6.dll`** 被加载了 —— 两套 MinGW 运行库 ABI 不一致。
`selftest` 等命令从不创建 `ofstream`，所以躲过了；**`vectors` 是唯一写文件的子命令**，崩点正好在 `basic_ofstream` 构造里。

**修法**：`build.ps1` 加 `-static-libstdc++ -static-libgcc`（已加，并写了注释说明为什么不能省）。
重建后 `cross_check.py` **9 项全过**，且 C++ 算出的 `‖center(f_B·c_B)‖∞ = 361` 与本项目 Python 侧独立算出的 361 完全一致。

> 这条也写进了 `README.md` §6 环境坑。它不改变任何算法，但**解开了被卡住的 `cross_check.py` 工作流**（README §3 一直在推荐它）。

### 3.2 模拟结果不可复现（同 seed 换跳数范围数字就变）—— 已修

**症状**：同一个 `seed`、同一批样本，**只改模拟的跳数范围** `--max-hops`，`δ(h)` 就会变：

```
EES1171, seed=1, 30000 样本
  max_hops=22 → h=21 的失败数 = 2779
  max_hops=30 → h=21 的失败数 = 2730
  max_hops=42 → h=21 的失败数 = 2753
```

差异约 1σ 的 MC 噪声量级 —— 所以**不是数值错误，估计仍然无偏**，但**不可复现**：
换个跳数范围重跑就得到不同的数字，这在写报告/复核时是硬伤。

**根因**：`simulate_curve` 用**一条全局 RNG 流**。每个批次消费的随机数个数是
`max_hops × 2`（每跳两个多项式），所以**第 2 批以后的链完全取决于 `max_hops`** ——
第 1 批不受影响，其余全部换了一批样本。

**修法**：每个批次用 `(seed, 批次号)` **独立播种**，切断批次间的流依赖：

```python
rng = xp.random.default_rng([int(seed), bi])   # bi = 批次序号
```

**验证**：同一 seed 下 `max_hops` 取 22/30/42 现在给出**完全相同**的计数（930/930/930）✓

**为什么要记这一条**：它解释了一类现象 —— 报告里早期版本的数字与后来略有出入
（如 EES1171 的 δ(21) 从 8.82% 变成 9.08%），原因就是不同批次是在**不同的 `--max-hops`** 下跑的。
现在这类差异不会再出现了。

它拿 C++ 引擎**真实算出来的密文**（`f_B`、`C_B`、`M`、`g`、`s`、`e`、`F_A`）反推出噪声核，与我们的模型公式逐位比对 —— 模型公式不是我推完就算数，是被实数验过的。

过程中还澄清了 vectors 导出的两个表示问题（写进注释，避免后踩）：
- 导出的 `FA` 其实是 **`f_A`**，要 `F_A = (f_A − 1)/p` 才能还原（`1` 只在常数项）；

- `f_B·C_B` 必须**先归约 mod q 再取中心代表**，才是环里真正的"小多项式"。

## 5. 论文 Table 4 口径核对

**读到了论文原文**（Nuñez, Agudo, Lopez. *NTRUReEncrypt: An Efficient Proxy Re-Encryption Scheme
Based on NTRU*. ASIA CCS 2015），解开了两件事，
也暴露出一个比原来更精确、但**仍未完全解决**的问题。

#### (1) "~10% 失败率"是我们自己的解读，不是论文的定义

论文原话：`# Hops` = **"the average number of re-encryptions supported"** ——
即"平均能撑几跳才解密失败"，是一个**停时统计量**。论文从没说过它对应 10% 失败率。

那个"~10%"的说法来自外部模拟器（`A1-4_选题方案/`，已丢失），
**在设计文档里被当成论文口径写了进去**。这一条要改。

#### (2) Table 4 是 8 行，设计文档只取了其中 4 行

元组 `(n, prod, k)`，`prod` = 是否用 **product-form 多项式**。见 `最终报告.md` §3.5 的表。
设计文档的 `paper_hops`（5/21/21/50）= **"no" 四行**；我们的模拟器模拟的正是非 product-form。

#### (3) 换成论文自己的定义，反而**另外三个对不上**

按论文定义算 `E[H] = Σ_h P(撑过 h 跳) = Σ_h (1 − δ(h))`：

| 参数集 | 论文 #Hops（no 行） | 我们 `E[H]` | 我们 `h@δ=0.1` | 我们 `h@δ=0.5` |
|---|---|---|---|---|
| EES439 | 5 | 8.0 | 6 | 8 |
| EES1087 | 21 | **20.9** ✅ | 16 | **21** ✅ |
| EES1171 | 21 | 28.4 | **22** ✅ | 28 |
| EES1499 | 50 | 62.7 | **49** ✅ | 63 |

**两种定义各对上一半、互相矛盾**：
- 用 δ≈10% 的跳数：EES439 / EES1171 / EES1499 对上（±1 跳），**EES1087 差 5 跳**。
- 用论文自己说的 `E[H]`：**只有 EES1087 对上**（20.9 vs 21），另外三个都偏高 60% / 35% / 25%。

这说明**"哪个统计量"这个解释不足以解决问题** —— 如果只是口径不同，
换一个定义应该四条一起对上才对。所以差异更可能来自**实现层面**（见下）。

#### (4) 标度律检查：我们的模拟本身是自洽的

噪声核每跳增量 `σ_W ≈ 3√(4·dr·df/n)`，失败判据是固定阈值，所以"失败率相同的跳数"应当
**正比于 `1/σ_W²`**。拿它当第三个标尺：

| 参数集 | `1/σ_W²`（归一） | 论文 #Hops / 5 | 我们 `h@δ=0.1` / 5 |
|---|---|---|---|
| EES439 | 1.00 | 1.0 | 1.0 |
| EES1087 | **3.16** | **4.2** | **3.0** |
| EES1171 | 4.37 | 4.2 | 4.2 |
| EES1499 | 10.06 | 10.0 | 9.6 |

我们的模拟比值（1.0 / 3.0 / 4.2 / 9.6）与 `1/σ_W²`（1.00 / 3.16 / 4.37 / 10.06）**四条全吻合** ——
说明**我们自己的模拟是自洽的，没有单独在 EES1087 上出错**。
偏离 `1/σ_W²` 标度的是**论文的 EES1087 值**（4.2 而标度律给 3.16）。

⚠️ **但这条不能用来断定"论文错了"**：`σ_W` 是拿**我们的参数**算的。
若我们的 EES1087 参数与论文原本的不同，标度律的"预期值"和我们的模拟会**一起**偏，这条测试就分不出来。

#### (5) 结论：**不能声称复现，也不能声称论文有误**

三个标尺（δ≈10% 的跳数 / `E[H]` / `1/σ_W²` 标度）**各自指向不同的结论**，
且没有一个能让四行同时对上。所以现在的状态是：

> **论文 Table 4 与我们的模拟在 EES1087 上不一致，根因未定。**

**报告里只能这么写**：
- ❌ 不能写"四个参数集全部复现了论文 Table 4"
- ❌ 也不能写"论文 Table 4 有误"（证据不足以定性）
- ✅ 可以写"我们的模拟与论文 Table 4 在 3 个参数集上一致（同一失败量级下相差 ≤1 跳），
  在 EES1087 上存在未解释的差异；并且论文的 `# Hops` 定义（平均可支撑跳数）与
  常用的'固定失败率下的跳数'不是一回事，两者应按各自口径分别引用"

#### (c) 噪声模型也核对无误

**`f = 1 + p·F` 得到确认** —— 这一条很关键，因为 ntru 库**不是**这么做的：
`NtruEncrypt.java:486` 写着 `if fastFp=true, f=1+3*priv_t; otherwise, f=priv_t`，
而 `fastFp=true` 只对应 **product-form（_FAST）** 变体。普通参数集若照库的默认走，
`f` 就是普通三元（系数 ±1），`f ≢ 1 (mod p)`，我们整套噪声模型都不成立。

**但作者在 `NTRUReEncrypt.java:182-189` 里无条件覆盖了它**：

```java
public IntegerPolynomial privatePolynomial(EncryptionPrivateKey priv) {
    IntegerPolynomial f = extractF(priv);
    f.mult(3);        // f = 3t
    f.add(one);       // f = 1 + 3t   ← 不管 fastFp 是什么
    return f;
}
```

**⇒ 论文 Table 4 是 `f = 1 + p·F` 下跑出来的，和我们的 `src/core/ntru.cpp` 一致。**
（这也印证了设计文档那句"`f ≡ 1 (mod p)` 是正确性的必要条件" —— 作者的 `decrypt`
确实是直接 `m = (f·c mod q 的中心代表) mod 3`，不乘 `f^{-1} mod p`，所以必须 f ≡ 1。）

作者的重加密噪声：

```java
Polynomial r = generateBlindingPolynomial(generateSeed());
IntegerPolynomial ruido = r.toIntegerPolynomial();
ruido.mult(3);                                  // × p
IntegerPolynomial c_prime = c.mult(rk.rk);
c_prime.add(ruido);                             // c' = c·rk + p·r
```

`r` 由 `SparseTernaryPolynomial.generateBlindingPoly(ig, N, dr)` 生成 ——
源码里 `ones[]` 和 `negOnes[]` 都是长度 `dr`，**是平衡三元（dr 个 +1、dr 个 −1）**，
与我们 `sample_fixed_weight(dr, dr)` 完全一致 ✓。噪声重量也确实等于 `dr`（= df），
与我们的 `de = P.dr` 一致 ✓。

#### (d) 一处小差异（影响可忽略）

EES1087/1171/1499 的 `maxM1 = 0`，意味着**明文里没有 −1 系数**；我们建模成 `dm1 = dm0`。
实测量级：它只进常数项 `C0`，而 `C0` 的方差在 h=21 时只占总噪声的 2%，
**对跳数的影响 < 0.1%**。但 439 那组 `maxM1=126` 是有 −1 的，修正时应一并改。

也就是说，**论文 Table 4 里 "(1087, no, 256) = 21" 这一格看起来才是那个异常值。**

#### (f) 审计汇总：C2 的数字依赖 `src/core/` 的 7 个设计决定

逐条对着**作者本人的实现**核过（可核的都核了）：

#### (g) 一个需要留意的疑点：PoC 里的 `generateSeed()` 是写死的

作者的 `NTRUReEncrypt.java:191`：

```java
private byte[] generateSeed() { return new byte[]{1, 2, 3, 4}; }   // 写死！
```

`generateBlindingPolynomial(generateSeed())` 因此**每次返回同一个 `r`** ——
加密噪声和**每一跳的重加密噪声都完全相同**。若 Table 4 是在这个状态下跑的，噪声会
**随 h 线性增长**而不是我们的 `√h`，跳数会远小于我们算的值。

**但这条大概率不成立**：我们的 `√h` 模型对 `(439,no)`、`(1171,no)`、`(1499,no)` 三行
都吻合到 ±1 跳；若是线性增长，这三行会差得离谱。所以 Table 4 应该是用**随机种子**跑的，
这个 `{1,2,3,4}` 只是这个 PoC 测试版的遗留（`README` 与 `src/core/sampler.h` 也都提到过这件事）。
**记录在此，万一将来发现哪组数字异常可以先怀疑它。**

### 6.2 队友的 C++ 实现 vs 作者实现 —— 差异清单

把 `src/core/` 和作者的实现逐项对照过。**8 项差异里只有 1 个是真 bug，1 个是建模选择分歧，其余是作者 PoC 的遗留。**

#### 一致的部分（都核过源码）

## 7. 已知限制与不确定度

1. **深尾外推的绝对数值只有量级意义。** `δ(1)` 从 `4.7e-15`（EES439）到 `1e-81`（EES1499），这些数字**完全依赖经验 CGF 的二次延拓**，而延拓的锚点 t_max 受样本量限制。
   **已做敏感性实测**（EES439，MC 曲线固定，只变 CGF 样本数）。
   这条结论可复现，就是一条命令：

   ```bash
   python pyref/mc_failprob.py --params EES439 --cgf-sweep 50000,200000,800000
   ```

   实测值（40000 样本的 MC）：

   | CGF 样本数 | t_max | δ(1) | δ(2) | δ(3) | h_max(2^-40) | h_max(1e-6) |
   |---|---|---|---|---|---|---|
   | 5 万 | 0.0554 | 7.4e-13 | 1.7e-06 | 4.5e-4 | 1 | 1 |
   | **20 万**（默认） | 0.0726 | 1.9e-14 | 6.4e-07 | 3.6e-4 | 1 | 2 |
   | 80 万 | 0.0830 | 1.3e-14 | 6.5e-07 | 3.6e-4 | 1 | 2 |

   **结论：20 万以上已经收敛** —— 20 万 → 80 万，`δ(1)` 只差 1.5 倍，`δ(2)`/`δ(3)` 基本不动，`h_max` 稳定。5 万不够（`δ(1)` 偏 40 倍、`h_max(1e-6)` 差 1）。
   所以默认的 `--cgf-samples 200000` 是实测选出来的，不是拍脑袋；正式跑批不要往下调。
   - **实用结论稳**：EES1087/1171/1499 的 `δ(1)` 分别约 `1.4e-32` / `5.2e-51` / `1e-81`，都远低于 `2^-40`。
   - 报告里仍应把这些值写成"低于 X 量级"，因为模型还有 `最终报告.md` §3.5 那个漂移不确定度（实测 0.04~0.10 decade）。
2. **并集界 `δ ≈ n·p₁` 在 h 小时高估。** 这就是 `最终报告.md` §3.5 里那个漂移的来源，已在输出里量化，不能当作已解决。
3. **MC 可测下限**：CPU/fft 在 40000 样本下约 `δ ~ 1e-4`。要测到 `1e-6` 需要 `~1e7` 样本（`--backend cupy`，WSL）。
4. **两个 TINY 参数集（n=7 / n=61）噪声远小于 q/2，永不失败**，只能用于算术精确性验证，不能用于失败概率统计。
5. **两端口径**：C++ 引擎默认用 `mt19937_64`（`sampler.h` 有 CSPRNG 的 TODO）。C2 的模拟器同样用确定性 RNG，**只用于概率建模，不用于生成真实密钥**。
6. **`h_max` 的含义**：它是"δ ≤ 目标"的最大跳数。`h_max(2^-40) = 0`（EES439）意味着**连 1 跳都超预算** ——
   因为该方案**自身 1 跳的算术噪声底**（`δ(1) ≈ 1e-11`）就已经高于 `2^-40`。这是方案的固有属性，不是缺陷。
