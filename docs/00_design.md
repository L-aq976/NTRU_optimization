## 1. 算法实例化（与代码逐条对应）

环 `R = Z_q[x]/(x^n − 1)`，`q = 2048 = 2^11`，`p = 3`，参数集取 `net.sf.ntru` 的 EES 族。

| 步骤 | 公式 | 代码 |
|---|---|---|
| 私钥 | `F` 三元（df 个 +1、df 个 −1）；`f = 1 + p·F`（**注意 "1" 是常数项**） | `keygen` in `ntru.cpp` |
| 公钥 | `g` 三元（dg/dg）；`h = p·g·f^{−1} mod q` | 同上 |
| 加密 | `C = h·s + M`，`s` 三元（dr/dr），`M ∈ R/p` | `encrypt` |
| 解密 | `a = f·C mod q` → 取中心代表 → `M = a mod p`（输出 {−1,0,1}） | `decrypt_with_noise` |
| 委托 | `rk_{A→B} = f_A · f_B^{−1} mod q` | `rekeygen` in `pre_base.cpp` |
| 重加密 | `C_B = C_A · rk + p·e`（`e` 小多项式） | `reencrypt` |

**正确性**：
- 原始：`f·C = p·g·s + f·M = p(g·s + F·M) + M`（用了 `f = 1 + pF`）→ mod p 得 `M` ✓
- 重加密：`f_B·C_B = f_B·C_A·f_A·f_B^{−1} + p·e·f_B = f_A·C_A + p·e·f_B` → mod p 得 `M` ✓
- 噪声：`‖center(f·C)‖_∞` 实测（EES439）约 141（原始）、417（重加密），远小于 `q/2 = 1024` ✓

**两个实现要点（都已在代码里注释）**：
1. `f ≡ 1 (mod p)` 不是优化，是**正确性的必要条件**（`f` 出现在明文那一项上）。
2. `p·e` 也不是可选项：没有它，接收者用 `f_B·C_B = f_A·C_A` 就能直接解出 `f_A`（只要 `C_A` 在 `R_q` 中可逆）。

**已知安全缺陷（必须写进报告，不许回避）**：
- `rk · f_B = f_A`：**代理 + 任一接收者合谋 → 直接得到委托方私钥**（零成本，不需要格约化）；
- `rk` 是"小多项式 / 小多项式"的形状，可被多密钥 NTRU 格攻击恢复私钥（Liu–Pan–Zhang, [ePrint 2019/083](https://eprint.iacr.org/2019/083) 及 2024 年多项式时间版本）；
- 抗合谋 NTRU PRE 已有前人工作（JISA 2023, *A provably secure collusion-resistant identity-based proxy re-encryption scheme based on NTRU*）→ **本项目不主张"抗合谋"，主张的是"提高腐化阈值"**。

## 2. C1：门限多代理委托（核心设计）

### 2.0 C1 解决的是什么场景、什么问题（报告第一章直接用）

**场景**：云数据共享 / 跨机构数据授权。
Alice 把加密数据放在**第三方**（云、网关、跨部门的数据交换平台）上，并把"解密权"委托给 Bob（医生、审计员、下游系统）。
在标准 PRE 里，这个"第三方"就是**代理**，它持有委托凭证 `rk_{A→B}`。

**问题（C1 针对的正是这个）**：

1. **凭证是单点**：`rk` 是一个环元素，谁拿到它谁就拥有**完整的、不可分割的**委托权。现实里的"代理"往往就是一个服务商、一个网关、一台机器 —— **单点信任**。
2. **单点腐化 = 彻底失守，而且失守得极其廉价**：
   - `rk · f_B = f_A`：代理与接收者（或偷到 Bob 私钥的人）**合谋一次**，直接得到 Alice 的私钥，不需要任何格约化；
   - 更糟的是 `rk` 是"小多项式 ÷ 小多项式"的形状，即使不勾结接收者，也可能被多密钥 NTRU 格攻击恢复私钥（[ePrint 2019/083](https://eprint.iacr.org/2019/083) 及 2024 年多项式时间版本）；
   - 一旦 `f_A` 泄露，泄的不是"被委托的那部分数据"，而是 **Alice 用这把钥匙加密的全部数据**（包括从未打算委托给 Bob 的对象）。
3. **没有容错**：代理宕机/被隔离，委托链路直接断掉。

**C1 的做法与其收益**：

把 `rk` 用"子集加性分享"拆成 `n` 份分给 `n` 个代理（可以是不同云、不同部门、不同地域），**任意 `t` 个才能完成一次转换**：

| 维度 | 传统单代理 PRE | C1 门限版（t-of-n） |
|---|---|---|
| 腐化阈值 | **1** 个代理（+ 接收者）即全部失守 | **t** 个代理合谋才可能（`≤ t−1` 个零信息，信息论可证） |
| 与接收者合谋 | 拿到任意 1 份 rk 就能算 `f_A` | 单份份额是均匀随机的，合谋也算不出 `rk` |
| 容错 | 代理挂了就断 | `n−t` 个代理可下线，服务照常 |
| 组合门槛 | 无 | 需要 t 份部分结果（可指定 `n` 个代理中任意 t 个） |
| 代价 1：噪声 | 1 份 `p·e` | `C(n,t−1)` 份噪声之和（实测放大 1.7~2.7×）→ 多跳上限下降 |
| 代价 2：计算 | 1 次重加密 | t 份部分重加密（**互相独立，天然可并行 —— 正是 C3/GPU 的落点**） |

**必须同时说清的三条边界**（否则会被误当成"抗合谋"）：

- 这**不是抗合谋**：`t` 个代理合谋仍能重构 `rk`，进而得到 `f_A`。C1 做的是"把腐化阈值从 1 提到 t"；
- 这**不是**新的安全模型下的证明（不是 CCA / 不是 HRA），只是把委托凭证的**信任结构**从单点改成门限；可证的部分只有"≤ t−1 份份额零信息"（信息论，见 §2.2）；
- 前人工作：LWE 上有格上门限多代理 PRE（`papers/28`《通信学报》；Zhao et al., Information Sciences 2024 的属性门限 PRE）。**NTRU/`x^n−1` 上的门限多代理委托需要第 1 周查重确认**（见 `A1-4_选题提案_NTRU方向.md` §6）。

### 2.1 为什么不能用 Shamir（这是本项目最有技术含量的一步）

`q = 2048 = 2^11`，**`Z_q` 不是域**，而是局部环（极大理想 `(2)`）。Shamir 的重构系数

```
λ_i = Π_{j≠i} (0 − j)/(i − j)
```

分母 `(i − j)` 只要含因子 2 就**不可逆**。取整数点 `1..n` 时所有差都是偶数 → 全部不可逆 → Shamir 直接失效。
（换素数模数也不行：`rk` 必须活在 `Z_2048[x]/(x^n−1)` 里，重构结果必须精确等于 `rk mod 2048`，不能只等于某个大素数模下的值。）

### 2.2 采用的方案：CNF / 子集加性分享

（Ito–Saito–Nishizeki 对门限访问结构的经典构造）

- 子集大小 `s = n − t + 1`，共 `C(n, t−1)` 个子集；
- 每个子集分一份随机份额，**最后一份由"总和 = rk"反解**；
- 代理 `P_i` 持有所有包含 `i` 的子集份额（每人 `C(n−1, t−1)` 份）；
- 转换时：`partial_S = C_A · share_S + p · e_S`，组合者把全部 `C(n,t−1)` 份相加。

**为什么正确**：`Σ_S share_S = rk`，且**重构系数全是 1**（不用求逆、噪声友好）。
**为什么任 t 个就够**：`|S| = n−t+1 > n−t = |[n]\W|` ⇒ 每个子集必与参与集合 `W` 相交。
**为什么 t−1 个不够**：`|[n]\W| = n−t+1 = |S|` ⇒ 恰有**唯一**一个子集与 `W` 不相交，该份额均匀随机，`W` 看到的总和与 `rk` 独立（信息论意义下零信息）。

代码：`cnf_share` / `proxy_partials` / `threshold_combine`（`src/core/threshold.cpp`），测试覆盖 `(3,2)(4,2)(5,2)(5,3)(6,4)(4,4)`。

### 2.3 噪声代价（会进入 C2 的预算）

每个子集各加一次 `p·e_S`，所以组合后的噪声是 `C(n,t−1)` 份独立小噪声之和。
实测（`n=61` 的测试参数，基线重加密噪声 = 72）：

| (n,t) | 子集数 C(n,t−1) | 门限噪声 | 相对基线 |
|---|---|---|---|
| (3,2) | 3 | 87 | 1.21× |
| (4,4) | 4 | 144 | 2.0× |
| (5,2) | 5 | 168 | 2.33× |
| (5,3) | 10 | 191 | 2.65× |

**读法**：噪声随子集数的增长明显**慢于线性**（典型是 `√C(n,t−1)` 量级，因为各份噪声相互独立、取的是 ∞-范数的最大值）。
这就是"门限化的代价曲线"，也是报告里可以拿出去的核心图之一：**安全阈值 ↑ 换取的噪声预算 ↓ → 可支持跳数 ↓**。

### 2.4 待验证命题（**必须自己推一遍再写进报告**）

1. **partial 的泄漏边界**：若 `partial_S = C_A·share_S + p·e_S` 被别的代理看到，由 `·C_A^{−1}` 再 mod p 可恢复 `share_S mod p`；而 `Σ_S share_S = rk`，且 `f_A ≡ 1 (mod p)` ⇒ `rk ≡ f_B^{−1} (mod p)`，**泄漏的只是接收者自己公钥的信息**。
   → 结论：部分密文可以不广播，但即使泄漏也无害；正式报告需给出完整推导。
2. **组合者的信任位置**：组合者（或领头代理）会看到全部 partial。它是否会因此获得 `rk` 的额外信息？按上面第 1 条，只有 mod p 的信息。
3. **`e_S` 的重量选择**：目前用 `P.dr`（与加密噪声同分布）。是否需要按门限层数放大？需要用噪声预算实验确认。

## 5. 不能声称的东西（答辩红线）

1. 不能说 NTRUReEncrypt "安全"——它已被攻破；我们只主张**腐化阈值从 1 个代理提高到 t 个代理**（且这条在信息论层面可证）。
2. 不能说"抗合谋"（前人已做，且我们的构造里 `t` 个代理合谋仍可恢复 `rk`）。
3. 不能说"首次用 GPU 做格上 PRE"（Dai–Doröz–Sunar 做过 NTRU GPU；Sahu–Rohloff CANS 2020 做过格上 PRE GPU）。
4. 演示用的 `n=61` 沙盒参数**安全性为零**，只能用于功能验证；任何性能/安全结论都要标注参数集与安全级别。
